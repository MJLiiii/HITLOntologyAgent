# Registered synthetic tasks

`synthetic-task-v1` supports more than the fixed ownership example. It is a separate development-only engineering protocol. The original `demo-v1` and `model-pilot-v1` inputs and fixed-demo admission check remain unchanged. Real-domain task activation and a real study remain unauthorized.

The application registers a task from an immutable candidate revision under its accepted synthetic scope, with a task ID and instruction. The server must verify the current base/head, scope, engine configuration, resolved synthetic document evidence, required question oracles and recorded decisions for additional tests. Those workflow authorization checks are distinct from this module's pure schema/hash checks. A string containing a reviewer or decision ID is not independent proof of approval. Direct Python access is not an authentication boundary.

`freeze_synthetic_task` accepts task ID/instruction, source bundle digest, base and seed ontologies, full development questions, tests, shapes, global fixtures, evidence and reviewed mappings. It returns `FrozenSyntheticTask.packet_json`, `.digest` and `.to_dict()`. The JSON is an immutable, serialized boundary; `.to_dict()` returns a fresh copy. Exact RDF/query/evidence text is preserved, including literal lexical forms and prefix-looking text inside literals. No query text substitutions occur. The registration digest covers all stored packet fields.

`execute_synthetic_task(packet, registration_digest=..., settings=..., ...)` rechecks the registered digest and reparses the strict packet. It admits only synthetic classification, development split, the fixed demo namespace and RDFS profile. Unknown fields, held-out flags, unsupported ontology predicates, executable SHACL extensions, out-of-namespace RDF subjects, malformed/remote queries and duplicate identities are rejected before model calls. Query support is the generator's bounded local basic ASK/SELECT subset; the real Jena parser remains the execution authority. Complex accepted SHACL Core constraints remain subject to Jena validation and resource bounds.

Every required test must match its frozen competency question's ASK structure and expected Boolean; explicit prefix aliases may differ without changing parsed terms. Every question retains a required test. Additional development tests need `oracle_status=accepted` and a recorded `oracle_decision_id`; the application resolves that decision against immutable project state before registration. Per-test fixture hashes, evidence membership and reviewed mapping metadata are checked. Required tests cannot supply an alternate fixture that changes the question's evaluation graph.

The shared A–D mechanism retains one initial model call per task/replicate. A stops there. B self-revises without test or assessment reports. C can receive only failed required development CQ Boolean outcomes, up to the same repair budget as B. Additional reviewed tests, SHACL/SELECT outcomes and OntoCheck diagnostics are excluded from automatic repair feedback. D references C's exact automated candidate, history and physical call IDs, then waits for an actual human workflow. No reviewer, decision, elapsed review time or post-review output is fabricated. A valid later D review appends a separate sealed record and reruns the same registered evaluation inputs.

All automated outputs freeze before their common final evaluation. Each arm uses identical registered questions, accepted tests, shapes, global fixtures, base ontology and reviewed mappings. Source evidence and plain question text reach the model; query/oracle bodies, shapes, fixtures, mappings and evaluator data do not. Model failures remain scheduled observations with missing candidates and error statuses. The legacy fixed model pilot still rejects a different development workload.

Packet bounds are 20 questions, 100 tests, 20 resolved evidence records, 100 reviewed mappings, one MiB per ontology/test input, 100,000 characters each of shapes/global fixtures, and three MiB total serialized packet. The frozen model context must fit 64 KiB. Each model call allows at most 100 triple operations and 4096 output tokens; B/C/D allow at most two repair attempts, with the configured timeout capped at 120 seconds. All use the same configured model within the execution. These are engineering limits, not study-design approval.

Mixed-suite metrics distinguish Boolean answer cases from other checks. `reasoning_pass_rate` uses every scheduled ASK, SELECT and SHACL case, including expected violations and engine failures. Answer TP/FP/FN/TN, precision, recall, F1 and required/evaluable accuracy use **ASK cases only**. `case_counts.answer_scheduled`, `non_answer_scheduled` and `unevaluable` expose those denominators; `unevaluable` refers to ASK answers. A SELECT row mismatch or expected SHACL violation is not a Boolean false positive.

Verification includes two distinct authored tasks (`billing`, `inventory`) with their own seed graphs, sources, questions, global fixtures and case IDs. Unit tests check frozen equality across arms, tamper/split/oracle rejection, missing candidate retention, mapping identity, prefix/literal preservation, allowed feedback and D review lineage. Real confined Jena and OntoCheck tests run both task packets with an explicitly scripted model double: A/B fail the missing hierarchy question, C/D pass after the controlled repair, and all retain exact shared inputs. Those tests establish software behavior, not actual model performance or independent research observations. A live model study still needs all external gates in `protocol.yaml`.
