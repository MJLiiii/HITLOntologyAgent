# Studio frontend contract

The Studio is a React/TypeScript application with a standalone Vite development entry and a TrustGraph IIFE plugin entry. All workflow reads and writes go through the project-owned same-origin `/api/v1` API. No service secrets or automatic approvals are embedded in the browser.

`make api-contracts` exports the actual FastAPI OpenAPI document to `docs/openapi.json` and deterministically generates request, response, and operation types in `apps/studio-plugin/src/api/openapi.ts`; `make check-api-contracts` checks reproducibility. `generated.ts` contains generated response aliases for component imports. Feature calls use fixed OpenAPI operation keys with checked path/query parameters, headers, request bodies, and inferred responses. Job polling uses the generated job envelope and infers each endpoint’s result type from the server-declared job kind. Backend response models validate returned payloads and preserve absent fields separately from explicit nulls (`exclude_unset`). Stable response models reject unknown fields; report diagnostics retain their declared extensible payloads. Historical response metadata may omit artifact IDs or scope/mapping fields recorded only by newer versions; the UI preserves the available hashes and raw manifests, omits unavailable artifact links, and does not invent missing provenance. Authorization and workflow constraints remain authoritative on the server. `python scripts/export_openapi.py --check` performs the same generated-artifact freshness check directly.

## Experience

A persistent left navigation exposes Chat, Ontology, Sources, Proposals, Validation, and Experiments. Project, demo classification, approved version, and corpus snapshot remain visible. Chat is the first screen: an evidence-grounded conversation, inspectable citations, and ontology triples returned with answers. Ontology includes read-only approved vocabulary and immutable version history. Proposals combines revision diff, evidence, expert review, and publication. Validation separates logical checks from vocabulary/fitness assessment. Experiments includes A–D filters and export.

Sources also exposes the current scope, saved immutable scope versions, explicit human scope decisions, and staged Turtle seed import. Editing the scope/domain label does not select an organizational study domain: this deployment remains restricted to the synthetic demo and its fixed namespace. Saving scope clears its acceptance. A seed import creates an unvalidated proposal against the inspected frozen corpus; it never creates an approved version.

The visual design uses a light warm canvas, white panels, navy text, indigo actions, subtle borders, compact tables, and a narrow persistent context rail. Responsive navigation collapses on small screens. Every action has a disabled/loading/error state and eligible-state reason. Source/model content is rendered as escaped text.

## API contract

The endpoint notes below describe the fields used by the interface; the generated OpenAPI document defines complete shapes and required/nullability constraints. Paginated list responses are `{items: T[], next_cursor: string | null}`. Synthetic tasks use the standard page envelope. TrustGraph discovery uses the shared-cursor envelope documented below. The UI follows all discovery pages before presenting the complete list. API errors are `{code, message, details?, correlation_id?}`. Identifiers are opaque strings. Dates are ISO strings. JSON responses should not include secrets. Decimal metrics are fractions (0–1), and unavailable metrics are null with an optional reason.

- `GET /session` → actor, mode and model mode. An existing authenticated cookie or operator-provided `X-OE-Session-Token` establishes the human session. The frontend consumes a `#session=…` bootstrap fragment, clears it after success, and never persists the token in browser storage. An unauthenticated browser shows a local token entry form.
- `GET /projects` → project list. Project: `id, name, domain, description?, approved_version_id, corpus_snapshot_id, pending_publication_id?, scope_digest, scope_accepted, review_policy_id?, mode?` (`mode: demo` for synthetic fixture).
- `GET /projects/{p}` → Project.
- `GET /projects/{p}/scope` → current ScopeVersion, including the initial reference when no scope version has been saved: `id: string | null, title, purpose, namespace, digest, status?, accepted, competency_questions, shapes_ttl, fixtures_ttl, created_at?`.
- `GET /projects/{p}/scopes` → saved immutable ScopeVersion list. Historical scopes are inspectable, never accepted by silently switching the current scope.
- `POST /projects/{p}/scope` → append a scope version with `{title, purpose, namespace: "https://example.org/oe-demo/", competency_questions, shapes_ttl, fixtures_ttl}`. Each question is `{id, question, sparql_query, expected: boolean, required: true}`. One to twenty unique IDs; only explicit boolean ASK oracles are supported. The server parses SPARQL/Turtle. Saving resets scope acceptance and does not mutate earlier candidate bundles.
- `POST /projects/{p}/scope-decisions` → explicit human decision with `{scope_digest, decision: "accept" | "reject", rationale}`. The UI refreshes the current scope digest before posting and requires a written rationale. A negative ASK expectation means non-entailment in the test graph, not proof of negation.
- `POST /projects/{p}/seed-imports` → JobRef from `{ontology_ttl, corpus_snapshot_id, profile: "rdfs", rationale}`. Available only before the first approved release and without a pending publication. The UI accepts pasted Turtle or a local `.ttl` file, bounded to 1 MiB and the server's 100-operation change limit. Successful result is `{proposal_id, revision, bundle_digest}`; validation, assessment, review, acceptance and publication remain separate.
- `GET /projects/{p}/versions` → Version list. Version: `id, label, created_at, commit?, parent_version_id?, status, triple_count, class_count, property_count, triples: Triple[], reviewer?, source_snapshot_id?, publication_id?, bundle_digest?, manifest?`.
- `GET /projects/{p}/documents` → SourceDocument list. Source: `id, title, edition, classification, status, created_at, chunk_count, content_hash, artifact, rights, ingestion_run_id, ingestion_status, extraction`. Ingestion and extraction fields can be null. Extraction diagnostics describe incomplete processing; the document list does not return source text. Status distinguishes `uploaded`, `queued`, `processing`, `complete`, `incomplete`, `failed`; source responses may include ingestion/extraction diagnostics.
- `POST /projects/{p}/documents` multipart `file, title, edition, rights, classification` → SourceDocument. The local source adapter accepts UTF-8 `.txt`/`.md` and text-based `.pdf`, up to 20 MiB. Incomplete PDF extraction remains visible and cannot enter a frozen corpus.
- `POST /projects/{p}/ingestions` `{document_id, configured_flow_key: "default"}` → JobRef.
- `POST /projects/{p}/corpus-snapshots` `{ingestion_run_ids}` → immutable snapshot. Document response `ingestion_run_id` identifies its completed processing run.
- `GET /projects/{p}/trustgraph-ingestions?cursor=…&limit=…` → `{configured, items, preparations, next_cursor}`. A shared page contains at most `limit` total receipts and preparations (default 50, maximum 200) in stable creation-time/ID order. The UI follows the opaque cursor and combines both arrays before calculating recoverable preparations, so receipts on later pages are considered; repeated cursors produce an actionable error. The optional Sources panel renders ingestion controls only when configured. Receipts retain their upstream `queued`/`failed` status; a successful submission job does not establish completed extraction.
- `POST /projects/{p}/trustgraph-ingestions` `{document_id}` → JobRef. The server fixes the source binding, workspace, collection, flow and seed. This path accepts UTF-8 text; PDFs retain the local ingestion path.
- `GET /projects/{p}/trustgraph-ingestions/{id}/chunks?cursor=…&limit=…` → `{chunk_uris, source_id, provenance_artifact, selection_required: true, upstream_completion_supported: false, next_cursor}`. Pages default to 50 identities, maximum 200. The cursor binds the project, ingestion and source-graph artifact hash; changed upstream discovery returns a conflict instead of combining graphs. The UI loads every page before showing any choices and retains the bound provenance. These are registered identities, not verified previews. Selection starts empty and allows up to 50 explicit choices.
- `POST /projects/{p}/trustgraph-snapshots` `{ingestion_run_id, chunk_uris}` → JobRef. A successful frozen corpus includes `provider_snapshot.chunks` with exact verified quotation, source span, chunk hash, upstream chunk URI, source graph and extraction subgraph identities. The UI displays that selected evidence only after verification, refreshes the project corpus, and explicitly leaves global upstream completion unverified.
- `POST /projects/{p}/trustgraph-ingestion-recoveries` `{preparation_id}` → JobRef. The explicit recovery action only reattaches a proven existing upstream submission, never resends an absent one. Preparations without receipts remain inspectable with their seed/configuration metadata.
- `GET /projects/{p}/proposals` → full Revision list; list cards use: `id, title, revision, status, base_version_id, bundle_digest, created_at, summary?, stale?, validation_run_id?, assessment_run_ids?`.
- `GET /projects/{p}/proposals/{id}/revisions/{r}` → Revision: summary fields plus `rationale, additions: Triple[], deletions: Triple[], evidence: Evidence[], assumptions?: string[], history: {revision, status, created_at}[], validation?, assessment?, approval_ids?, review_eligibility?: {eligible: boolean, reasons: string[]}`.
- `POST /projects/{p}/proposal-jobs` `{base_version_id, corpus_snapshot_id, competency_question_ids: [], instruction}` → JobRef.
  Empty competency-question IDs focus generation on the whole scope. A nonempty list must contain unique IDs from that scope and focuses the model context and retrieval; every mandatory scope question remains in the frozen validation bundle. Unknown or duplicate IDs fail before generation or candidate writes. The labelled deterministic demo still produces its fixed synthetic proposal.
- `POST /projects/{p}/proposals/{id}/revisions` `{parent_revision, structured_changes: {additions: Triple[], deletions: Triple[]}, rationale}` with `If-Match` revision → Revision.
- `POST /projects/{p}/validation-jobs` `{proposal_id, revision, bundle_digest}` → JobRef.
- `POST /projects/{p}/repair-jobs` same bundle request → JobRef. The UI offers repair only after failed validation on a current candidate with no pending publication. The backend admits failed competency-question diagnostics only, bounds attempts to two per proposal, and returns `{proposal_id, revision, bundle_digest, repair_attempt}` for the successor. Required checks must run again; no acceptance is implied.
- `POST /projects/{p}/assessment-jobs` same request → JobRef.
- `POST /projects/{p}/test-generation-jobs` `{proposal_id, revision}` → JobRef whose result contains `{id, status: "needs_review", digest, revision_id, bundle_digest, tests}`.
- `GET /projects/{p}/test-suites` → TestSuite list. Queries, fixtures, rationale and expected results are displayed as untrusted data. The oracle panel exposes `generator.mode/version/oracle_policy`, `coverage_gaps`, per-test scenario/question/change IDs, oracle source, assumptions, exact candidate/fixture hashes and bound `fixture_artifacts`. SHACL conformance and full `expected_violations` signatures (`focusNode`, `path`, `sourceShape`, `severity`) are visible; SELECT rows preserve typed literal values/datatype/language and exact/contains comparison semantics.
- `POST /projects/{p}/test-oracle-decisions` `{test_suite_id, test_suite_digest, decision, rationale}` → decision or new successor Revision after acceptance. Human oracle acceptance preserves required sentinels and does not validate or approve the successor.
- `POST /projects/{p}/review-submissions` `{proposal_id, revision, validation_run_id, required_assessment_run_ids}` with `If-Match` → eligibility/revision response.
- `POST /projects/{p}/reviews` `{proposal_id, revision, bundle_digest, validation_run_id, required_assessment_run_ids, decision, rationale, review_policy_id}` → ReviewDecision.
- `POST /projects/{p}/publications` `{proposal_id, revision, bundle_digest, approval_ids, expected_head}` → PublicationRef.
- `GET /projects/{p}/publications/{id}` → exact publication receipt with status, candidate/revision identifiers and approval IDs. A pending receipt is not displayed as a completed publication.
- `GET /projects/{p}/reviews/{id}`, `/validation-runs/{id}`, and `/assessment-runs/{id}` → exact read-only decision or report. Version provenance links these records and distinguishes the inspected historical version from the current approved head.
- `GET /projects/{p}/audit` → audit list: `action, entity, actor, time, event_hash, previous_event_hash, sequence?, detail_digest?`. The UI filters related version/publication/review entities and offers the whole project chain; recorded hashes are not presented as client-verified signatures.
- `GET /projects/{p}/review-sessions?revision_id=…&cursor=…&limit=…` → a standard page of the current actor's persisted timing events. The UI consumes every page before deriving the latest timer state. `POST` to the same collection with `{revision_id, event: "start" | "pause" | "resume" | "end"}` → event with `active_seconds` and `time`. Timing writes require explicit clicks. The running display labels its local live estimate separately from the server-recorded duration; navigation neither starts nor ends a session.
- `POST /projects/{p}/question-jobs` `{question, history?, proposal_id?: string, revision?: number, corpus_snapshot_id?: string}` → JobRef. Without a candidate selection, the ontology is the approved head or visibly unapproved demo reference. The Chat source selector defaults to **Ontology version sources**, omitting a corpus override so historical sources remain bound to that version. Explicit **Current source corpus** selection sends the exact current project corpus ID and warns that it may be newer and does not approve or change the ontology. Response `source_selection` (`ontology_version`, `project_current`, or `explicit`), `corpus_snapshot_id`, and limitations remain visible on each answer even after the selector changes. Proposal and revision must be supplied together; a differing corpus override for a candidate is rejected rather than changing its bundle.
- `GET /jobs/{id}` → `{id, status, progress?, stage?, result?, error?}`. `result` is inline for this slice; answer result: `{answer, evidence: Evidence[], triples: Triple[], version_id?, limitations?: string[]}`. Proposal result includes `proposal_id, revision`; validation/assessment result includes report.
- `GET /projects/{p}/experiments` → Experiment list: `id, condition, task_id, replicate, status, created_at, vocabulary_coverage?, vocabulary_utilisation?, strict_fitness?, approximate_fitness?, answer_precision?, answer_recall?, elapsed_seconds?, correction_seconds?, workload_id?, phase?`.
- `POST /projects/{p}/experiment-jobs` `{protocol_id: "demo-v1" | "model-pilot-v1", condition: "A" | "B" | "C" | "D" | "all", task_ids: ["demo-ownership"], replicate_ids: [1]}` → JobRef. The UI explicitly chooses deterministic demonstration versus configured model pilot; both remain synthetic development workloads.
- `GET /projects/{p}/synthetic-tasks?cursor=…&limit=…` → `{items, next_cursor}` with immutable registrations (default 50, maximum 200). The selector includes all pages. Registration fields: `id, task_id, instruction, proposal_id, revision_id, revision, bundle_digest, registration_digest, protocol_id: "synthetic-task-v1", packet, created_at`. The third experiment protocol requires selecting one registration; run rows, condition counts and means are scoped to its unique task ID and remain separated by review phase.
- `POST /projects/{p}/synthetic-tasks` `{proposal_id, revision, bundle_digest, task_id, instruction}` → immutable SyntheticTask. The form chooses a displayed exact revision and requires a unique lowercase task ID plus instruction. Registration controls require a human researcher and an accepted demo scope; the backend rechecks eligibility and digest. The packet link and complete registration/bundle digests are inspectable. Registration does not approve an ontology or authorize a real study.
- `POST /projects/{p}/synthetic-task-jobs` `{registration_id, registration_digest, condition, replicate_ids: [1]}` → JobRef. The explicit run action uses the selected packet, not the demonstration task ID. These remain synthetic engineering model runs with failures and absent measurements retained.
- `POST /projects/{p}/experiments/{run_id}/proposal` without a request body → unapproved Revision for a waiting model D pre-review run, including `synthetic-task-v1`. Staging never runs validation, records a decision, or publishes. An explicit subsequent click opens Proposals.
- `GET /projects/{p}/reviews?revision_id=…` → paginated persisted ReviewDecision records, including accept/request_changes/reject. The revision ID is the distinct `revision_id`, not the proposal `id`.
- `POST /projects/{p}/experiments/{run_id}/review-results` `{review_id}` → new immutable post-review Experiment. Only a fetched human decision can be selected; linking requires an explicit authorized-human click. The backend verifies exact candidate ancestry, bundle and reports. The pre-review record remains unchanged. Missing/incomplete review timing remains null; a rejection or request for changes remains right-censored for time to acceptance.
- Experiment responses additionally expose `protocol_id, phase, parent_run_id?, linked_review_id?, candidate_digest?, candidate_ttl?, model?, repair_history?, validation?, assessment?, review_status?, evaluation_status?, limitations?`. The UI keeps protocols separate and suppresses aggregate fitness across mixed phases. Frozen candidate/reports remain read-only.
- `GET /projects/{p}/experiments/export?format=csv|json` → download containing all protocols/phases and failed outcomes.

`JobRef = {job_id, status_url?, correlation_id?}`. Async creates and publications send a fresh `Idempotency-Key`. Browser polls jobs until succeeded/failed/cancelled with bounded polling and errors visible. Writes refresh current project/revision to detect changed heads.

`Triple = {subject, predicate, object, object_type?: "iri" | "literal", datatype?, language?}`.

`Evidence` contains `id, document_id, title, quote, locator, chunk: ArtifactRef, content_hash, source_hash, span_start, span_end, adapter, status, created_at, resolved: boolean`, with optional extraction/provider provenance. When recorded, chunk artifact identity is `chunk.id`; older references can retain only their hash and artifact metadata. The UI explicitly labels unresolved evidence and cannot treat a generated quotation as verified evidence.

`Validation = {id, status, profile, engine?, created_at?, cases: {id, name, status, message?, expected?, actual?}[], limitations?: string[]}`. Engine is an object with `name, version?, runner_version?`. Status includes passed/failed/error/timeout/unsupported/not_run. Failed expectations differ from broken engines. Expected and actual values can be booleans, objects, or row arrays.

`Assessment` contains `id, status`, optional nullable coverage/utilisation/strict/approximate/structural fitness metrics, competency questions, reviewed mappings, and limitations. Successful assessment uses `completed`. Questions contain `id, question, sparql_query` and optional expected/required flags; they are labelled as included in the assessment, with no individual pass inferred. Frozen mappings contain `requirement_iri, ontology_iri, relation_type, rationale, evidence_ids, reviewer, review_id`. Approximate support never establishes OWL equivalence.

## Build and verification

Use exact dependency pins and lockfile. `npm --prefix apps/studio-plugin run dev` serves the standalone app and proxies `/api` to configurable local FastAPI. `npm --prefix apps/studio-plugin run build` type-checks and builds standalone plus plugin artifacts. Component tests verify displayed failures/errors, immutable revision requests, stale approval disablement, authorization errors, and escaped source text. A real backend smoke checks the complete safe review loop. The actual pinned TrustGraph host/template smoke is recorded separately in `docs/evidence/portal-smoke.md`; shared identity and full native ingestion remain separate gates.
